# ТЗ на розбірну 3D-модель (VELNOX)

Документ для передачі 3D-моделеру / підряднику.
Мета: модель на сторінці товару має **розбиратися на деталі**, кожна деталь —
**клікабельна**, з **підказкою** (назва + опис) і, за потреби, **посиланням на товар**.

Приклад цільової сторінки: `https://velnox.eu/uk/products/bearings/buq-309-2t3h`

---

## 0. Стан на сьогодні (факти з поточних файлів)

Перевірено `public/models/*.glb` (BUQ-309-2T3H, BUCR-SG-309-S2, BUP-207-X3L, PL-140, BAA-0004):

| Що | Як зараз | Наслідок |
|---|---|---|
| Ієрархія | `Root → "BUQ 309-2T3H (默认)" → "默认" → 10 мешів` | Деталей як об'єктів **немає** |
| Групування мешів | по **матеріалу** (`color`, `texture-2`, `polished platinum`) | Не можна виділити «внутрішнє кільце» |
| Імена вузлів | ієрогліфи + технічні назви KeyShot | Немає за що зачепитись у коді |
| Камери/світло | в файлі: `SOLIDWORKS Viewport`, `Default Camera`, `线光源4-7` | Зайва вага, конфліктує з нашим освітленням |
| Анімації | немає | Розбирання неможливе |
| Стиснення | немає (Draco/Meshopt) | 8–11 МБ на модель |

**Висновок:** поточні файли — це «одна злипла деталь». Розбирання/тултипи на них
не реалізуються в принципі. Потрібен новий експорт за правилами нижче.

**Хороша новина:** пайплайн SOLIDWORKS → KeyShot → glTF уже ріже геометрію **по матеріалах**.
Тобто якщо моделер призначить **окремий матеріал кожній фізичній деталі** — потрібна
ієрархія з'явиться майже без додаткової роботи.

## 1. Відповіді на три питання власника

| Питання | Відповідь | Умова |
|---|---|---|
| Чи можна розібрати/зібрати модель? | **Так** | Кожна деталь — окремий вузол + заданий вектор і порядок розбирання (розділ 4) |
| Чи можна тултипи по кожному елементу? | **Так** | Унікальний матеріал на деталь (клік-пікінг) + точка прив'язки підказки (розділ 5) |
| Чи можна гіперпосилання на товар? | **Так** | Тільки для деталей, які реально продаються окремо. Решта — підказка без посилання або кнопка «Запит на деталь» |

Тексти підказок і посилання — **не в моделі**. Вони живуть у нас (БД / i18n),
бо їх три мови (uk/en/pl) і вони змінюються без переекспорту 3D.
Від моделера потрібні **тільки** геометрія, імена та координати.

## 2. Формат файлу

| Параметр | Вимога |
|---|---|
| Формат | glTF 2.0 binary — **`.glb`**, один файл |
| Осі | **Y-up**, права система координат (стандарт glTF) |
| Одиниці | 1 unit = **1 метр**. Підшипник Ø90 мм → 0.09 unit |
| Початок координат | центр посадкового отвору (вісь обертання) на **(0,0,0)**; вісь вала — вздовж **Z** |
| Стан за замовчуванням | **зібраний** виріб (t = 0) |
| Камери | **видалити всі** (`Default Camera`, `SOLIDWORKS Viewport`) |
| Джерела світла | **видалити всі** (`KHR_lights_punctual` не використовувати) — освітлення на сайті через HDR-середовище |
| Backplate / студійні площини | **видалити** (`3 Point Faded`, `3 Point Faded Backplate`) |
| Матеріали | тільки PBR metallic-roughness |
| Текстури | ≤ 2048×2048, JPG/PNG; за можливості KTX2/Basis |
| Стиснення геометрії | **Draco** або **Meshopt** обов'язково |
| Вага фіналу | **≤ 6 МБ**, цільове 3–4 МБ |
| Полігони | 300–600 тис. трикутників на весь виріб. Тесселяція CAD: відхилення ≤ 0.05 мм, кут ≤ 10° |
| Іменування | **тільки ASCII**: латиниця, цифри, дефіс, підкреслення. **Жодних ієрогліфів, кирилиці, пробілів, дужок** |

## 3. Ієрархія та іменування — ядро ТЗ

### 3.1 Структура

```
Root
├── VX-01-housing
├── VX-02-outer-ring
├── VX-03-inner-ring
├── VX-04-ball-set
├── VX-05-cage
├── VX-06-seal-a
├── VX-07-seal-b
├── VX-08-grease-nipple
└── VX-09-setscrew
```

Правила:

1. **Один вузол = одна фізична деталь.** Вузол має власний меш. Плоский список під `Root`
   (без проміжних груп типу `默认`). Підвузли допускаються лише для складених
   вузлів (наприклад, `VX-04-ball-set` → окремі кульки), але кожна група має бути ціла.
2. **Однакові дрібні деталі** (кульки, болти одного типорозміру) — **один вузол** з усією
   геометрією: `VX-04-ball-set`, `VX-09-setscrew` (усі гвинти разом). Це знижує вагу
   і кількість підказок. Якщо болти різні — окремі вузли.
3. **Нумерація `NN` має збігатися з позиціями на нашому кресленні** (`schema.svg`
   на сторінці товару). Тобто поз. 3 у кресленні = `VX-03-...` у моделі.
   Список позицій моделер отримує від нас **до початку роботи**.
4. **Ім'я меша = ім'я вузла = ім'я матеріалу.** Три однакові рядки.
5. **Півот (origin) кожної деталі** — у її власному геометричному центрі або на осі обертання.
   Трансформ **не запікати у вершини**: вузол має свій `translation`, геометрія — у локальних
   координатах відносно свого півота.
6. Порожніх вузлів, допоміжних площин, ескізів, ref-геометрії — **не має бути**.

### 3.2 Матеріали — критично для кліку по деталі

> **Кожна деталь має власний унікальний матеріал**, навіть якщо візуально
> матеріал однаковий (два ущільнення з одного каучуку → `VX-06-seal-a` і `VX-07-seal-b`
> як два окремі матеріали з ідентичними параметрами).

Причина: наш вьювер визначає, на яку деталь клікнув користувач, за матеріалом
у точці кліку. Спільний матеріал на двох деталях = неможливо їх розрізнити.

## 4. Розбирання і збирання

Потрібні **обидва** пункти нижче. JSON — обов'язковий, анімація — бажана.

### 4.1 JSON з векторами розбирання (обов'язково)

Файл `<ARTICLE>.parts.json` поруч із `.glb`. Для кожної деталі:

- `dir` — напрямок «виїзду» деталі, одиничний вектор у координатах моделі;
- `distance` — на скільки метрів відсунути в повністю розібраному стані;
- `order` — порядок розбирання (1 = знімається першим). Порядок збирання = зворотний.

Вимоги до розкладки:
- у повністю розібраному стані **деталі не перетинаються** і не заходять одна в одну;
- розкладка читається з основного ракурсу (як на кресленні «вибуховий вигляд»);
- рух — **прямолінійний**. Якщо деталь фізично викручується (гвинт, гайка) — вказати
  додатково `rotation` (вісь + кількість обертів).

### 4.2 Запечена анімація в .glb (бажано)

Кліп з ім'ям **`explode`**:
- `t = 0` — зібраний стан; `t = 1.0 s` — повністю розібраний;
- інтерполяція **LINEAR**, ключі тільки на початку і в кінці кожного руху
  (без easing — плавність додамо на сайті);
- кліп має коректно програватися **у зворотному напрямку** (це і буде «збирання»);
- покрокове розбирання: рухи деталей рознесені в часі за `order` — деталь `order: 1`
  рухається в проміжку 0.0–0.2 s, `order: 2` — 0.2–0.4 s тощо. Таймкоди продублювати в JSON.

## 5. Точки прив'язки підказок (hotspot anchors)

Підказка «висить» на конкретній точці поверхні деталі. Для кожної деталі в JSON:

- `hotspot.position` — точка **на видимій поверхні** деталі, координати моделі,
  **у зібраному стані**;
- `hotspot.normal` — нормаль поверхні в цій точці (щоб маркер ховався, коли деталь
  повернута від камери).

У розібраному стані координату ми перерахуємо самі: `position + dir × distance × прогрес`.

Точку обирати на найбільш «показовій» грані деталі, не на ребрі й не в отворі.

## 7. Комплект здачі

На один артикул:

1. `<ARTICLE>.glb` — фінальна модель за розділами 2–4;
2. `<ARTICLE>.parts.json` — за схемою розділу 8;

## 8. Схема `<ARTICLE>.parts.json`

```json
{
  "model": "BUQ-309-2T3H",
  "unitScale": 1.0,
  "axis": "Y_UP",
  "explodeDuration": 1.0,
  "parts": [
    {
      "node": "VX-01-housing",
      "material": "VX-01-housing",
      "order": 1,
      "explode": { "dir": [0, 1, 0], "distance": 0.12, "timeFrom": 0.0, "timeTo": 0.2 },
      "hotspot": { "position": [0.031, 0.048, 0.0], "normal": [0, 1, 0] }
    },
    {
      "node": "VX-02-outer-ring",
      "material": "VX-02-outer-ring",
      "order": 2,
      "explode": { "dir": [0, 0, 1], "distance": 0.08, "timeFrom": 0.2, "timeTo": 0.4 },
      "hotspot": { "position": [0.045, 0.0, 0.012], "normal": [1, 0, 0] }
    },
    {
      "node": "VX-09-setscrew",
      "material": "VX-09-setscrew",
      "order": 3,
      "explode": {
        "dir": [1, 0, 0], "distance": 0.05, "timeFrom": 0.4, "timeTo": 0.6,
        "rotation": { "axis": [1, 0, 0], "turns": -3 }
      },
      "hotspot": { "position": [0.052, 0.010, 0.0], "normal": [1, 0, 0] }
    }
  ]

```

Поля `title`, `description`, `productSlug` моделер **не заповнює** — їх додаємо ми з БД.

## 9. Чекліст приймання (перед оплатою)

```bash
npx @gltf-transform/cli inspect BUQ-309-2T3H.glb
```

- [ ] Кількість вузлів = кількості деталей у кресленні (+1 `Root`)
- [ ] Усі імена ASCII, за шаблоном `VX-NN-slug`
- [ ] Кількість матеріалів = кількості деталей (жодного спільного)
- [ ] Немає камер, немає `KHR_lights_punctual`, немає backplate
- [ ] Є `KHR_draco_mesh_compression` або `EXT_meshopt_compression`
- [ ] Вага ≤ 6 МБ
- [ ] Модель відкривається в зібраному стані, центр — у (0,0,0), масштаб реальний
- [ ] Кліп `explode` є, зворотне програвання дає коректне збирання
- [ ] `.parts.json` валідний, усі `node` збігаються з іменами у `.glb`
- [ ] У розібраному стані деталі не перетинаються
- [ ] Нумерація `NN` збігається з позиціями на `schema.svg`

## 10. Реалізація на сайті (для внутрішнього планування)

Поточний стек: `<model-viewer>` 3.4.0 з Google CDN
(`ProductTemplate/blocks/VisualPanel.tsx`, `PhotoGallery.tsx`), без three.js у залежностях.

**Варіант A — залишаємось на `<model-viewer>`.**
Клік по деталі — через `materialFromPoint(x, y)` (тому й потрібен унікальний матеріал
на деталь). Розбирання — програвання кліпу `explode` з керуванням `currentTime` зі
слайдера. Підказки — нативні hotspot-слоти, позиції перераховуються на кожному кроці
розбирання через `updateHotspot()`. Нових залежностей у бандл не додається.
Перед запуском робіт потрібен спайк на пів дня — підтвердити поведінку
`materialFromPoint` і `updateHotspot` на реальній моделі.

**Варіант B — three.js / react-three-fiber.**
Повний контроль: raycast по мешу (ім'я вузла напряму, унікальний матеріал не обов'язковий),
підсвітка деталі, розбирання рахуємо з `dir × distance` без запеченої анімації,
HTML-підказки. Ціна: +~600 КБ до бандла та більший обсяг робіт.

Рекомендація: **A**, і переходити на **B** тільки якщо спайк покаже обмеження.
ТЗ вище сумісне з обома варіантами — переробляти модель при зміні варіанту не доведеться.

**Окремо про вагу.** Зараз моделі 8–11 МБ і вантажаться по кліку «Завантажити 3D модель».
Розбірна модель важча за структурою, тому Draco/Meshopt у ТЗ — не побажання, а умова.
